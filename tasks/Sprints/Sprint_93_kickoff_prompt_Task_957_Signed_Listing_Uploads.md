## Goal

Listing photos go from the browser straight to Cloudinary with an unsigned preset, so anyone who reads the page uploads any file into any folder of the account, including another person's `<userId>/listings` (X-01); a listing (through the Server Actions or directly through PostgREST) accepts any photo address of the cloud. After the task: no unsigned preset exists; the browser still uploads directly to Cloudinary (the body stays off the Vercel function, whose limit is 4.5 MB), but each photo needs a signature the server issues for that session, for one server-chosen `public_id` under the owner's folder, with `overwrite=false`, so a repeated request stores nothing new; signatures are limited per account; the database refuses a photo outside its listing owner's folder. A photo is traceable both ways: Cloudinary shows the uploader's `#public_id` and listing in the asset's metadata, and the admin copies an account's UUID (the folder name) from its profile and finds an account by a pasted folder name. A daily job deletes listing and avatar uploads no row uses after 7 days and the owner folders left empty; a deleted account's whole folder goes, except a file a row still uses. The synthetic users and listings (`zz_synth_…`) of a test run that CI cancelled or killed are removed by the same job, and any older one by the next CI run (O957-5). The browser jobs take Chromium and its system packages from a cache written only by `main`, so a slow package mirror no longer runs a job out of time (O957-6).

## Cause

Read at `a9915f3ba`
- The widget uploads with an unsigned preset and a browser-chosen folder: `src/modules/listings/components/ImageUpload.tsx:181-190` (`uploadPreset={uploadPreset}`, `folder: uploadFolder`); the preset name is public: `src/app/[locale]/listings/create/page.tsx:22`, `src/app/[locale]/listings/[slug]/edit/page.tsx:103-104`. `node scripts/quality/cloudinary-config.mjs` → "U1 the preset named by NEXT_PUBLIC_CLOUDINARY_UPLOAD_PRESET: unsigned: anyone who knows the name uploads any file into the account" (2026-11-18).
- A photo address is checked only for the cloud: `src/lib/uploads/imageUrl.ts:20` (the path starts with `/<cloud>/`); its comment `src/lib/uploads/imageUrl.ts:6` ("Images are uploaded by the server") is false for listing photos. A session writes `listing_images.url` directly (`supabase/catalog.json:2535`, INSERT and UPDATE of `url` granted to `authenticated`), and the only check is the cloud prefix (`supabase/catalog.json:3009`, `listing_images_url_prefix_check`). Today all 200 `listing_images` rows lie under `/<listing owner>/listings/` (read-only count on the development project, 2026-11-18), so the stricter rule rejects no stored photo.
- No shared limiter exists: the reveal limit counts its own table (`src/modules/listings/actions/contactGateway.ts:39`); the sliding `consume_rate_limit` was planned in Task 959 (`tasks/Sprints/Sprint_93_kickoff_prompt_Task_959_Auth_Abuse_Keys_Data_Exposure.md:53`), not built.
- Cloudinary: "Signatures are valid for one hour from the timestamp value used to generate the signature" (cloudinary.com/documentation/authentication_signatures); whether one signature serves several uploads: the docs do not say (UNKNOWN), hence O957-2. "parameters provided directly in the upload request take precedence over the same parameters defined in the upload preset" and "Upload presets don't support a per-preset file size limit" (cloudinary.com/documentation/upload_presets). `next-cloudinary` 7.0.0 spreads `options` into the widget options after its own `uploadSignature` (its `dist/CldUploadWidget-*.cjs.js`), so the widget's `prepareUploadParams` reaches Cloudinary.
- Cloudinary's `prepareUploadParams` "only supports preparing the following parameters", among them `context`, `overwrite`, `publicId`, `signature`, `tags`, `uploadPreset`, not `allowed_formats` (cloudinary.com/documentation/upload_widget_reference), so the signed preset bounds the formats.
Fix: a signature route that issues per-photo signed parameters chosen by the server (owner folder, random `public_id`, `overwrite=false`, preset, uploader metadata) after the session, owner and limit checks; the widget gets them through `prepareUploadParams`; the limiter and a `listing_images` owner-folder trigger in SQL; the owner check in the two Server Actions; U3 in `cloudinary-config.mjs`.

## Attack surface

Changed: a new authenticated endpoint, the photo upload path, the photo acceptance of listing writes (application and database), a new SECURITY DEFINER function.
- T1 Spoofing / elevation: a stranger or another account uploads into a person's folder — mitigate: only an active session gets a signature; the folder and `public_id` are the server's; a signed request cannot change them.
- T2 Denial of service (cost): unlimited uploads — mitigate: 30 signatures per 10 minutes and 200 per day per account; one signature stores at most one photo (`overwrite=false` on a fixed `public_id`, O957-2); the signed preset bounds the formats; the preset's incoming transformation bounds the stored size; a signature expires after one hour.
- T3 Tampering: a listing carries another account's photo — mitigate: `isOwnedListingImageUrl` in both actions and the trigger for direct PostgREST writes.
- T5 Elevation through the new definer function — eliminate: EXECUTE for `service_role` only, `search_path` empty.
- T6 Information disclosure: uploader metadata reaches Cloudinary — eliminate: only the pseudonymous `#public_id` and the listing id, never a name, e-mail or phone; the folder stays the opaque UUID.

Authorization matrix, `upload-signature`: anonymous 401; blocked account 403; active user, no listing (own folder) 200; active user, own listing 200; active user, another person's listing 403; moderator with `listings.moderate`, any listing 200 (owner's folder);
